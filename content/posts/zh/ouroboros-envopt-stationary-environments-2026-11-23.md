Coding Agent 可能在每次任務都重新搜尋數千個檔案、尋找相同的 API Endpoint，或反覆解析同一份試算表。除了更換模型或修改 Prompt，還有另一個可最佳化的變數：**重新整理 Agent 所存取的資訊，讓後續任務的成本降低。**

Li 等人於 **2026 年 11 月 5 日**提交的 [EnvOpt 論文](https://arxiv.org/abs/2611.07372)，研究如何自動改善多項任務共用的工作環境。這項研究與自主實驗系統直接相關，因為它讓研究 Agent 修改環境、執行另一個固定的目標 Agent，並依驗證成本與正確率決定是否保留變更。論文數字相當顯著，但方法的適用範圍、成本及驗證機制必須分開檢視。

## 修改的是環境，固定的是模型與 Harness

作者將 *Stationary Environment* 定義為許多任務共用、內容相對穩定的資訊集合，例如企業工作區、程式碼 Repository，或資料工程的 SQL 腳本目錄。底層事實不應任意改變，但其**呈現方式與存取介面**可以調整。

例如，原本需要逐一開啟數千個 SQL 檔案才能找到資料表的 Agent，可以改查預先建立的 SQLite 索引，直接取得資料表與原始檔案的對應關係。另一個環境加入 API Endpoint 速查表，減少反覆探索工具的呼叫；程式碼 Repository 則新增排序程式，讓 Agent 優先閱讀較可能包含 Bug 的檔案。這些變更涉及索引、存取路徑及衍生資料，並沒有更新模型權重。

EnvOpt 區分研究 Agent **R** 與固定的目標 Agent **T**。R 取得環境副本、在另一個 Sandbox 執行 T 的權限，以及有限的實驗預算。R 可以新增檔案、索引、資料庫和輔助程式，但對 T 的 Harness 所做的修改會被捨棄。這個限制很重要，否則觀察到的提升可能其實來自 Prompt 或工具權限政策的變更，無法歸因於環境本身。

[論文 Algorithm 1](https://arxiv.org/pdf/2611.07372) 把任務分成三組。Training Tasks 分批且互不重複，研究 Agent **無法取得標準答案的驗證器**。R 觀察目標 Agent 的執行軌跡、修改環境，再依成本與近似的答案一致性判斷保留候選。每輪結束後，另一組具有驗證器的 **Validation Tasks** 會檢查成本與正確率；若成本上升或正確率超過容許幅度地下降，就回退至上一版本。最後才使用未參與調整的 **Test Tasks** 報告結果。

這裡必須精確區分：**訓練階段不提供驗證器，不代表整套系統不需要驗證器**。停止條件依賴有正確答案的 Validation Set。隱藏訓練答案可以降低直接記住答案的風險，卻無法完全消除資料分布洩漏、代理指標誤判，或反覆使用驗證集造成的過度擬合。

## 論文實際測量了什麼？

AutomationBench 的 600 個公開任務中，作者抽取 **200 題作為最終測試、96 題作為驗證**，其餘供訓練使用，每輪使用 **20 個訓練任務**。研究 Agent 是 Claude Code 搭配 Opus 4.8；目標 Agent 是 Claude Code 搭配 Haiku 4.5。最佳化在第五輪停止。

[論文 Table 1](https://arxiv.org/pdf/2611.07372) 的測試結果如下：

| Benchmark／目標 Agent | 通過率：原始 → 最佳化 | 總成本：原始 → 最佳化 | 成本下降 |
| --- | --- | --- | ---: |
| AutomationBench／Haiku 4.5 | 2.33% → 16.67% | $42.36 → $11.55 | 72.73% |
| AutomationBench／Opus 5（跨模型轉移） | 33.83% → 35.17% | $236.18 → $75.26 | 68.13% |
| Workspace-Bench／GPT-5.4-mini | 39.84% → 43.12% | $12.55 → $6.57 | 47.65% |
| Data-Eng-Bench／GPT-5.6-luna | 50.68% → 53.88% | $16.13 → $7.51 | 53.44% |

表格的美元數字是 Benchmark 任務集合的 **API 總成本**，並非單次查詢價格。論文圖說指出 AutomationBench 的結果平均自三次獨立執行。通過率的差距以**百分點**計算，不能當成相對提升百分比。尤其 Haiku 4.5 的基準通過率只有 2.33%，增加 14.34 個百分點雖然顯著，但最佳化後仍有大部分任務失敗。

作者另報告將 EnvOpt 疊加在 Meta-Harness 的 Harness 最佳化結果上，對 Haiku 4.5 可再降低 **83.4% 成本**，並增加 **11.17 個百分點**的正確率。這支持兩種最佳化方式可能互補，但不足以保證所有 Harness 或資料集合都會有相同效果。

跨模型轉移尤其值得注意。針對 Haiku 4.5 最佳化的環境，可以直接交給 Opus 5 使用，無須修改 Opus 5 的模型權重或 Harness。然而，轉移後的正確率並非永遠上升：Workspace-Bench 的 Opus 5 從 **62.27% 降到 61.14%**；Data-Eng-Bench 的 GPT-5.6-sol 從 **62.56% 降到 61.19%**，即使成本同時下降。若部署政策不允許品質退化，就必須考慮統計不確定性和預先設定的容許門檻，不能只看成本。

## 經濟性：必須有足夠多的後續任務才能回本

離線最佳化本身需要研究 Agent 的推論成本與目標 Agent 的測試成本。論文 AutomationBench 的示例估計，一次離線最佳化約 **150 美元**；Opus 4.8 在原始環境下每題約 **1.73 美元**，最佳化後約 **0.39 美元**。以這組四捨五入後的數字計算，損益平衡點約為：

`150 / (1.73 - 0.39) ≈ 112 次查詢`

論文圖中標示 **109 次**，反映底層未四捨五入的抽樣數值。這是**特定場景的經濟性估算**，不是通用價格。如果環境經常改變、任務不常發生，或每次更新都需要重新驗證，前期成本可能無法回收。相反地，若有數千次任務重複使用相同資料，預先建立索引和輔助工具就可能有相當高的效益。

還必須計入資料完整性與安全成本。自動生成的索引可能過期；速查表可能漏掉必要的權限檢查；純文字匯出可能把敏感資訊複製到保護不足的位置。因此環境變更應有範圍限制、版本控制與獨立的語意一致性檢查。若 Benchmark 只獎勵減少 Tool Call，系統也可能偏好省略困難情況的捷徑。

[EnvOpt 公開 Repository](https://github.com/itea1001/EnvOpt) 目前明確註明，程式碼因 Server 問題**尚未完整公開**，因此獨立重現受到限制。上述結果全部是**論文作者報告的測量**，不是本文自行重現，也不是本地 Mac 的實測。論文沒有證明 oMLX 本地模型也能得到相同幅度的提升。

## 工程結論

EnvOpt 提供了具體、可測試的理由，將**資料與工具存取方式**視為獨立的最佳化變數。最強的證據在於：索引、Endpoint 指南及衍生搜尋程式，可以在數個固定工作環境降低重複任務成本，同時維持或改善測試表現。跨模型轉移確實可行，但有品質退化的例外。

對資源受限的自主研究系統，風險較低的第一個實驗，是固定模型與 Harness，針對不變的資料集合建立唯讀衍生索引，再以相同的保留測試題比較有無索引的結果。記錄通過率、每題成本、實際耗時和檢索失敗，並納入索引建立成本及更新政策。只有當事先定義的正確率容許門檻成立時，才接受最佳化環境。

這比一開始就允許 Agent 自行修改模型權重更容易驗證。現有證據支持**環境最佳化是一條有潛力、相對獨立的改進路徑**，但沒有證明它能帶來普遍、自動或零成本的自我改善。
